# TWWHD Randomizer core mod — experimental

This is a source port of **TWWHD Randomizer 1.2.0** through the guest mod SDK.
It runs on the **unmodified USA game**, using seed data and changed content from
the player's official randomized output. The randomized RPX is validated and
read as input; its executable code is not installed or executed by this route.

The core has source implementations, data preparation, private package building,
SDK integration and a desktop import flow. It remains experimental: **no full
randomized playthrough has been verified**. Windows and Android end-to-end use,
real boss/NPC/dungeon encounters, and the gameplay effects of every supported
option still need validation. USA is the only supported game build.

## Build and import a seed

You need:

- A complete, unmodified USA game folder from your own copy.
- The matching complete output folder generated by the official TWWHD Randomizer
  1.2.0. A content-only replacement or an isolated RPX is insufficient.
- A port release containing this experimental builder and its current SDK.
- A **PowerPC-capable Clang executable**. The importer does not download one.
  Apple's Clang has no PowerPC backend; a setup command such as `xcrun clang`
  cannot be used directly by this builder. An arbitrary native compiler or Zig
  command is not assumed compatible.

On desktop, open **Settings → Mods → More → Import randomized game**. Choose the
original USA folder and the randomized output folder. Select PowerPC Clang if
the setup compiler is unsuitable, then choose **Build and import**.

The compiler is checked before seed preparation. Work happens in a private
background directory, with phase progress. Cancellation finishes the current
step and suppresses installation. Compiler steps have time limits; cancellation
is not an immediate interruption of filesystem operations or arbitrary compiler
wrapper processes. Folder-based building is currently available on desktop;
Android's picker cannot select these extracted input folders.

A completed package goes through the existing mod installer and review. Accept
the code-mod and experimental confirmations, allow any required code-mod-support
rebuild, and restart to activate it. The original game installation remains in
place. The package stays off until the normal approval flow is completed.

To replace an active core with another seed, disable it and restart first, then
import the new package and follow the new confirmation/restart prompts. Seeds
use the same package ID, `twwhd-randomizer-core`.

**Keep generated packages private.** They contain player-owned game assets and
must not be committed or redistributed.

## Command-line development flow

Run these commands from this directory, using new private output directories:

```sh
python3 seed_prepare.py ORIGINAL_USA_GAME RANDOMIZED_GAME PREPARED --content
python3 seed_package.py PREPARED NEW_PRIVATE_PACKAGE \
  --base-game ORIGINAL_USA_GAME --randomized-game RANDOMIZED_GAME \
  --ppc-clang /absolute/path/to/powerpc-capable/clang
```

Import `NEW_PRIVATE_PACKAGE` with **Settings → Mods → More → Install from a file
or folder → Choose folder**. The preparation directory is development input,
not an installable package. Header-only preparation is deliberately insufficient
for package creation.

For a shipped release, `tools/core_randomizer.py` provides the combined worker.
It takes `--resources`, `--original`, `--randomized`, `--output` and
`--compiler-json`. The compiler argument is a JSON array with an absolute
executable, not a shell command. See [setup-code-mods.md](../../../docs/setup-code-mods.md)
for its invocation and the desktop flow. Release builds use the resource
manifest's public source inventory, guest SDK headers and git-free provenance;
they do not require a source checkout or compiler lookup on PATH.

### Required stack alignment

**Every PowerPC guest translation unit must use `-mstackrealign`.** The package
builder supplies it. Native game callers can provide only eight-byte stack
alignment, while Clang normally assumes sixteen bytes. Missing realignment can
produce invalid local pointers even when argument registers are correct.

Recompile and relink older guest ELFs, including separately compiled helpers.
A newer runtime, cache rebuild or repeat translation cannot repair an ELF's
missing prologue. `-mstack-alignment=8` alone is not the fix. This requirement
applies to PowerPC guest compilation, not the later native host-module compiler;
no runtime stack-copying workaround is used. See the
[SDK build instructions](../../../docs/mod-sdk-v2.md#build).

## Seed validation and generated data

Preparation validates the original USA identity, bounded randomized RPX input,
reviewed function variants, hook compatibility, data layouts and option domains.
Unknown, truncated or incoherent variants fail before a completed preparation
is published. Do not bypass the compatibility checks to accept another
randomizer version or hand-edit generated headers to silence a rejection.

The four private headers are:

| Header | Contents |
| --- | --- |
| `seed_init_data.h` | Startup state, starting gear, preferences and validated policies |
| `seed_reward_data.h` | Seed item/reward tables |
| `seed_resources.h` | Seed-dependent resource descriptors |
| `seed_boss_data.h` | Boss reward constants matching the randomized assets |

`--content` also prepares a verified content overlay. Language-pack/MSBT changes,
stage actors and other asset changes come from the player's randomized output.
The combined identity includes code-derived seed data **and the complete
randomized content digest**, including files unchanged from the original.

The package builder independently decodes the inputs again, checks prepared
headers and every overlay payload, compiles a fresh relocatable `mod.elf`, and
runs SDK inspection/translation over its functions and imports. It records
source/SDK hashes, compiler arguments/flags, ELF identity and hook/import data in
`source-port-build.json`. A previous diagnostic ELF is not reused. The runtime
manifest is written last, so a failed build or copy is not a completed package.

Generated headers, seed output, content overlays and compiled artifacts belong
in private directories. They are not public release inputs. The release builder
ships an explicit allowlist of authored source/tools/SDK declarations; new public
source dependencies must be added to `public-files.json` when required.

## Implemented policy families

The source is organized around complete game consumers and shared SDK adapters,
with generated seed data kept separate from code. Major groups include new-file
and starting-item initialization, progressive items and reward sources, dungeon
items and boss rewards, story/swordless availability, entrance/savewarp/spawn
behavior, ship/song behavior, resource/heap setup, and item/menu presentation.
The custom `SwOp` and `DngSw` actors register through the native actor-profile SDK.
Port traversal and quick-use settings compose through their SDK helpers rather
than being bypassed by source replacements.

Preparation decodes seed-selected starting gear/hearts/magic, damage multiplier,
swordless/clothes choices, starting location, shuffled entrances, chart reveal,
preferences and other supported initialization data. It also validates fixed
resource, title, actor and reward layouts required by these source consumers.
The decoder modules define the accepted domains; unsupported variants are errors.

The following optional executable policies have coherent source implementations:

| Policy | Selection/behavior |
| --- | --- |
| Classic mode | Validated together across its complete function group |
| Instant text boxes | Message/input handlers plus the randomized language-pack changes |
| Quiet Swift Sail | Omits the selected sail-transition sounds, preserving traversal settings |
| Remove music | Registers the reviewed music-return consumers only when enabled |
| Particle performance | Selects the reviewed particle/effect policy |
| Inverted sea compass | Decodes and applies the compass-axis option |
| Fixed Helmaroc RNG | Decodes and selects the reviewed fixed-RNG branch |

Optional flags are derived from validated seed input, not manually supplied
build switches. Missing mandatory preparation macros require regeneration.
Where a policy has no disabled replacement, OFF registers no corresponding
owner. This table describes implemented selection, not end-to-end gameplay
verification of each option.

## Saves, backups and states

The manifest requires mod manager 1.7.0 and explicitly constrains the game build
to USA. The generic `game_id` field alone is not a region check. Save ownership
uses provider `twwhd-randomizer` and the complete prepared seed identity.

At startup the runtime selects the seed's save folder, backups, save-folder
preferences and state slots before recovery or game loading. Ordinary saves
remain separate by default. An explicit `--save` is an intentional exact-folder
override; avoid it when relying on automatic isolation.

Portable states must belong to the same save namespace. Full states also check
module/profile identity and guest actor-profile compatibility before applying
memory. Do not force-load rejected states or assume a full state survives a
module update. A seed switch takes effect after restart, not during a live
session.

## Validation and remaining work

Host fixtures cover individual consumers, data decoders, failure paths, callback
order and mutable/captured fields. Selected bounded native comparisons and
save/profile/state checks supplement them. The translated heap/stack fixture
also tests real compiled PPC at both eight- and sixteen-byte entry alignment,
including stack arguments and caller-stack by-reference writes.

Private macOS runs with the corrected compiler flags have reached active Link
gameplay and exited cleanly for ordinary, swordless, combined-option and
required-dungeon fixtures, with isolated saves and unchanged vanilla sentinels.
Additional bounded checks cover a real Bombs field pickup, the item-get demo,
portable and ordinary saving, fresh-process restoration and inventory rendering.
Custom switch actors execute in real dungeon rooms: a gate with no required
dungeons opens, while a three-required-dungeon gate remains closed.

These checks do not establish completion of a randomized seed, the physical
source chest for that pickup, boss defeats, every option, all visible/audio
behavior, or Windows gameplay. Game-free CI runs the core and SDK suites on
Windows, Linux and macOS; it does not replace those gameplay checks.

For development, run the focused `test_*.py` files for changed consumers and the
source suite from this directory:

```sh
python3 -m unittest discover -s . -p 'test_*.py'
```

Compiler/translated tests need a suitable compiler, selected with
`WWHD_PPC_CLANG` where supported. SDK ownership checks must retain one owner per
replacement target and only reviewed host services. Use the SDK inspector's
actual allocation and declared heap when preparing native fixtures; do not copy
old region-size constants. Keep real-game checks bounded and fully isolated from
live saves and the main checkout.

The focused tests and Git history retain implementation/audit detail. A complete
randomized playthrough, real encounter/option validation and platform testing
remain required before calling this a supported player release.
